# 技术调研平台整体评审（2026-11）

> 范围：技术雷达、技术专题/热点议题、AI 调研，以及它们共同依赖的研究库、阅读入口、全站 UI 骨架。
> 方法：读代码与契约 + 本机真实渲染（Playwright 抓页面结构、可访问性、移动端布局）+ 抽检本机数据库 + 竞品公开资料核对。
> 结论面向"接下来做什么"，不追求功能清单的完整复述。

---

## 0. 一句话结论

**这是一套"工程完成度远高于产品完成度"的系统**：后台任务、证据账本、审核门禁、部署与契约都做到了很多商业产品没做到的程度，但用户从"看到一条信号"到"形成一个可复用的判断"之间，仍然缺一个自然的落点——看完之后没有出口。

三块业务不是平均地弱，而是**强弱分明**：

- 雷达：**供给与治理是强项，消费侧闭环是短板**。默认筛选把大部分内容挡在外面，卡片上也没有"判断"这个动作。
- 专题：**是一个完成度不低的只读聚类视图，还不是一个能参与的工作台**。议题点不开证据，专题不能自建，综述不能导出或转成研究。
- AI 调研：**过程可信度是真正的差异化**（方案确认、证据账本、事实核验、发布门禁），但入口太重、结果页把"读"排在"管"后面、成果没有出口（无导出、无公开分享），导致 96% 的研究停在草稿。

如果只做一件事：**把"判断"变成一等公民**——在雷达、议题、研究结果三个位置都能一键留下"我判断了什么"，并让这个判断被下次排序、专题和研究复用。这比再补十个功能更能改变产品的命运。

## 2. 我们到底做成了什么

先把资产说清楚，否则优化建议会变成"重做一遍"。

- **雷达管线**：多源同步 → 临时抓原文 → 分块摘要/评分 → 分层 → 站外阅读入口；带额度熔断、片段回退、来源级重跑、缺分修复、噪声物理删除与库外归档。这套"失败也能说清楚"的设计，比大多数内容聚合产品扎实。[TECHNICAL_OVERVIEW](../TECHNICAL_OVERVIEW.md)
- **专题管线**：候选聚合 → 议题抽取 → 带引用综述 → 关注/未读；有缓存失效、输入 hash、证据回链。
- **AI 调研**：对话澄清 → 方案确认 → durable job → 检索/写作/引用回链 → 事实核验 → 结论审查 → 修订/追问 → 入库。四种产物（研究稿/快速判断/Slides 提纲/网页简报）共享同一套证据语义。
- **Reader 扩展**：全文翻译（含图片文字覆盖）、选段解释、连续追问、本地收藏、可选平台同步；独立模式不要求账号。
- **研究库**：草稿/发布/归档、版本、服务端搜索与排序、质量门禁、知识卡片与个人语义索引（AnythingLLM 可选）。
- **平台底座**：NextAuth、Prisma、Postgres 全文索引、Admin 治理、LLM 用量审计、Docker/GHCR 部署、备份恢复演练。

工程规模（不含依赖）：Web 约 2.6 万行 TSX、测试约 2.1 万行、AI engine 约 5.4 万行 Python、E2E 约 5.9 千行、文档约 2 万行。**测试与文档的投入比例是健康的**，这也是这次评审能快速定位问题的原因。

本机数据（2026-11-10，开发/验收混合库，仅作趋势参考）：

|---|---|---|
| 雷达条目 | 3,735 | 精读 423 / 速读 1,521 / 噪声 1,762 |
| 精读对外可见 | 59 | 约 14%（9 月精读 193 条，仅 27 条满足公开门槛） |

## 3. 三个模块的真实体验

### 3.1 技术雷达：供给充足，出口缺失

**最短路径**：`/radar` 列表 → 点标题 → 右侧「文章概览」→ 读「为什么值得看」→「打开原文」离开平台。两次点击，然后人就走了。

**做对的地方**

- 分层不是装饰：精读/速读/噪声是产品语言，不是内部枚举；卡片上的层级、来源、形态一眼可辨。
- 默认站外阅读是正确取舍：不存全文、不做站内正文，规避了版权与排版两大坑。
- 治理能力是真的：负向反馈、软屏蔽、恢复、审计、引用保护，能长期维持信噪比。

**断点（按影响排序）**

1. **看完没有动作可做。** 卡片只有「收藏」，详情只有「写笔记 / 打开原文 / 用 Reader / 打开 Zread / 深入调研」。缺"已读 / 不感兴趣 / 稍后 / 值得试点"这些低成本判断。写笔记是重动作，收藏是无语义动作，中间空了。`RadarFeedbackBar.tsx:54` 定义了 5 种反馈，但默认只渲染 2 种（收藏、点踩）。
2. **判断不回流。** 收藏与反馈只用于治理保护，不影响下次排序；用户教了系统，系统不学。
3. **默认视图双重收窄。** 默认「近 7 天 + 精读」（`RadarScreen.tsx:144,307`）。本机数据里近 7 天为 0 条，首屏直接空态；空态会提示"可以查看全部时间"并给出按钮，但阅读等级/来源仍要用户自己翻筛选，没有"一键放宽"（`RadarScreen.tsx:826`）。
4. **精读反而最不可见。** 公开门槛要求 `external_reading` 标签或"正文/质量/审核三连 ready"。9 月 193 条精读里只有 27 条满足（14%），而同期速读 429/516 可见（83%）。**层级与可见性倒挂**：最该被读的内容被挡得最狠。`api/radar/route.ts` 的 `publicQualityGate`
5. **时间语义错位。** 卡片只显示"入库 9月2日"，不显示原文发布时间（`RadarCandidateCard.tsx:190`）。一篇 2024 年的旧文，在列表里看起来像今天的新闻。
6. **三套概览并存。** 列表内嵌预览、`/radar/[id]` 的 ExternalReadingLanding、详情底部 Reader 区块，能力各缺一块：预览不能收藏/讨论，详情没有讨论，卡片不能写笔记。用户每换一个入口就要重新学一次。
7. **"为什么值得看"可能是原文摘录。** `RadarExternalReadingLanding.tsx:117` 在 AI 判断缺失时直接拿 excerpt 顶上，界面上没有区分。对"AI 判断"的信任是一次性的，混一次就没了。
8. **搜索在分页后过滤。** API 先按 DB 分页取数，再在应用层 `matchesQuery` 过滤（`api/radar/route.ts` 尾部），页内条数会少于 total，翻页体验不可预期。

**结论**：雷达的问题不是"看不到"，而是"看完没有出口"。当前它更像一个**信息展示系统**，还不是一个**判断系统**。

### 3.2 技术专题 / 热点议题：完整的只读视图

**做对的地方**

- 专题页的叙事完整：定位语 → 综述（tldr / 关键变化 / 分节 / 开放问题 / 引用）→ 活跃议题 → 相关内容 → 相关研究，信息架构是清楚的。
- "议题"这个概念抓得准：技术雷达真正有价值的最小单位不是文章，而是"正在发生的一件有争议的事"。
- 相关性跟进（关注、未读横幅、上次查看后有更新）是对的留存设计。

**断点**

1. **议题点不开证据。** 列表只显示"29 条关联内容"，不渲染链接；`candidateIds` 明明已经在 props 里（`TopicDetailTabs.tsx:867-887`）。这是本次评审里**性价比最高的一个修复**。
2. **专题不能自建。** 7 个专题是预置的，提议由算法产出、Admin 审批（`topic_proposals`）；用户只能关注，不能定义"我想追什么"。对个人调研平台，这是根本性限制。
3. **热度是条数。** `hot ≥ 6 条、warming ≥ 3 条`（`topic_refresh_worker.py:115-119`），重要度 `0.3 + 0.1×条数`（`topic_issue_worker.py:461`）。UI 写"按重要度排序""正在升温"，但既没有时间衰减，也没有来源权重、讨论热度或用户反馈。专题新鲜度也停在 9 月 14 日。
4. **专题是死胡同。** 不能导出、不能转成研究、不能订阅（只有站内 follow + 横幅）、不能分享给同事。看完综述，下一步只能自己复制。
5. **内部词汇外泄。** 列表直接显示"20 个采集渠道""聚合窗口"，这些是运维指标，不是用户价值。
6. **列表能力薄。** 无搜索、无分页、`take: 80` 硬上限（`topics/page.tsx:51`）。

**结论**：专题目前是"同一批雷达换个视图 + 一段综述"，还没有产生新的用户动作。它离"团队技术决策的讨论场"只差三件事：**能点开证据、能自建、能带走**。

### 3.3 AI 调研：可信，但太重

**做对的地方（这是全产品最强的差异化）**

- **方案确认**：研究什么 / 交付什么 / 投入多少 / 参考什么，四组单选 + 可编辑重点 + 来源策略。Perplexity / ChatGPT 是一键开跑、过程黑箱；这里是"可干预的研究合同"。
- **证据账本**：来源快照、正文回链、声明级核验、覆盖门禁。绝大多数"Deep Research"产品只给引用列表，不给"哪条结论有证据、哪条没有"。
- **失败语义诚实**：evidence_only / partial / 无证据 brief 各有独立文案，"资料已保留 ≠ 结论"的表述克制准确。
- **异步与恢复**：durable job、租约、刷新恢复、多标签页防重、取消。
- **产物形态**：研究稿 / 快速判断 / Slides 提纲 / 网页简报，且 Slides 明确声明"不是 .pptx"，不夸大。

**断点**

1. **确认页把优势变成了门槛。** 默认值其实已经选好，多数人只需要点一个按钮，但要先滚过 6 组设置、4 个折叠区、3 处资料入口（`AiResearchBrief.tsx:633/742/959`）。**建议默认折叠成一条"方案摘要条"**（一句话 + 真实耗时 + 来源策略 + 修改），一键开跑。
2. **耗时与成本不可见，主按钮还在两屏之外。** plan API 返回 `estimatedMinutes`，但 UI 从未渲染，只写"几分钟到十几分钟"（`AiResearchBrief.tsx:542`）；配额提示只在失败后出现。实测确认页表单高 1,177px、滚动区 2,257px，「开始研究」按钮位于距顶部 2,023px 处——用户至少要滚两屏才能启动。等待 10–18 分钟却不知道还要多久，是最容易放弃的时刻。
3. **"AI 整理"名不副实。** plan 实际是关键词正则 + 模板（`plan/route.ts:41-58,125-178`），界面却写"AI 已根据问题整理，可调整"。在一个以"诚实标注证据"为卖点的产品里，这种文案是负资产。要么用一次 utility 模型调用真的做规划（成本极低），要么改文案。
4. **结果页把"读"排在"管"后面。** 正文之前堆了状态头、5 步 stepper、百分比、计数徽章、深度进度、证据、逐条审核。用户最想看的是结论。
5. **证据面板只给"问题清单"。** `ReviewClaimsPanel.tsx:87-90` 只渲染未解决的 claims，supported 的结论永不出现，"质疑这条依据"成了死分支。用户看不到"哪些话是有据的"，只能看到"哪些话有问题"。
6. **知识沉淀入口隐形。** "存为知识"只在选中一段文本后出现（`KnowledgeCardComposer.tsx:155`），没有常驻入口；而卡片发布又要求背景/风险/资料检查，卡片 Composer 根本不产出这些字段 → 知识卡片很难发布（会同时撞上事实审核门禁与背景/风险字段要求）（`api/knowledge/route.ts:59`、`publish/route.ts:178`）。
7. **成果没有出口。** 没有 Markdown/PDF 导出，没有公开分享页；`published` 只对登录成员可见。48/50 停在草稿，不是用户不想发，是发出去也没有用。
8. **会话与任务割裂。** "最近对话"过滤掉了已启动研究的会话（`AiResearchConversationSidebar.tsx:95`），调研完成后回来找不到入口。
9. **成功率 58.5%。** 失败/部分完成/取消合计 39/94。对 10 分钟级的任务，这个数字会明显损害信任。至少要区分"可重试失败"和"配置/额度失败"，并提供"稍后自动重试"。
10. **审核撑不住长报告。** 实测 31k 字的研究稿在"全文清单"阶段直接超时（`APITimeoutError: full-text inventory incomplete`），两次都返回 `unavailable`，发布按钮始终禁用；而产品是鼓励生成 3 万字长报告的。这是"生成能力"与"审核预算"的结构性错配。

**结论**：AI 调研的**过程设计**是领先的，**结果交付**是落后的。它现在像一份严谨的内部审计报告：可信，但不好读、带不走。

### 3.4 研究库与知识沉淀：门禁把成果锁在草稿里

- 列表能力完备（成果/草稿/我的已发布 × 类型 × 排序 × 服务端搜索 × 分页），但卡片没有类型徽标，"我的已发布"实际包含已归档（`research-list-where.ts:31`）且无标识。
- 发布门禁要求背景/结论/风险三个独立字段齐全。实测：本机 48 份草稿**全部**至少缺一个（其中 17 份事实审核已 passed 也一样），包括一份 39,761 字、35 节、正文里已有"结论/风险"章节的研究稿，发布按钮仍是禁用。发布率 4% 不是用户懒，是门禁形状不对。
- 同一状态有三套说法：私人草稿 / 草稿 tab / draft 徽标；卡片又同时是"类型"和"状态"。

**这是产品最可惜的一处**：花了大力气做证据与审核，最后却没有把"一条被验证过的判断"变成可复用的资产。

## 4. UI 与设计系统

**做得好的**

- **可访问性**：五个主页面 axe（WCAG 2A/AA）**0 violation**；有 skip link、aria-label、焦点管理、reduced-motion 处理。这在同类自研产品里很少见。
- **响应式**：390px 下主页面无横向溢出；雷达在移动端用底部抽屉筛选项，信息不丢。
- **状态完备**：加载、空、错误、禁用、部分完成都有独立组件与文案，不是"转圈到死"。
- **一致性**：MUI 9.5 + Emotion + 共享 design tokens，Web 与 Reader 同一套语义色；暗色主题有首屏防闪脚本。
- **任务可见性**：顶栏的"进行中调研"指示器（15s 轮询）是很实用的设计。

**需要改的**

1. **字体层级塌陷。** 12/13/14/15px 四档挤在 3px 区间，24px 标题下直接掉到 14px；列表页 12px 元素占多数；报告正文 13px/1.6。对一个"阅读与研究"产品，正文应 16px 起、长文 17–18px/1.8，元信息才用 12px。
2. **内部概念泄漏。** 阅读等级、目标层级、profile 原值（paper/engineering）、分层分/排序分/内容质量、否决项、采集渠道、聚合窗口——这些是运维语言，不是用户语言。
3. **嵌套滚动。** `shell.module.css` 用 `height: 100dvh` + `.main { overflow-y: auto }`，整站是应用式内滚动。代价：返回上一页时滚动位置通常丢失、移动端地址栏行为怪异、长报告无法整页打印或导出 PDF。
4. **三套阅读入口**（打开原文 / 用 Reader 阅读 / 打开 Zread）并列，主次不清；安装引导还会打断阅读。
5. **⌘K 名不副实**：只是 `router.push('/search')`（`Topbar.tsx:77`），没有浮层、没有最近搜索，落页输入框也不自动聚焦。
6. **没有首页/落地页**：`/` 直接 302 到 `/radar`。对内工具没问题，对外产品缺一个说明"这是什么、为什么值得每天看"的入口。

### 5.3 我们的真实位置

**优势（少数但真实）**

1. **可解释的分层治理**：市面上要么二元静音（Feedly），要么规则（Inoreader），要么人工半年一版（Thoughtworks）。"7 维评分 + 精读/速读/噪声 + 负向治理 + 引用保护"是稀缺的。
2. **可核验的研究过程**：方案确认、来源账本、声明级核验、发布门禁。通用 Deep Research 产品没有"结论 vs 证据"的对账。
3. **中文技术语境**：中文源、中文摘要、中文专题，Elicit/Perplexity 都不为中文工程团队优化。
4. **一体化闭环**：雷达 → 专题 → 调研 → 知识卡片 → 下次调研复用。单点都打不过专业产品，但闭环是独有的。
5. **工程可信度**：任务可恢复、失败可解释、部署可回滚，这是团队客户敢用的前提。

**劣势（会被放大的）**

1. **每一层都不是最好的**：发现不如 Feedly，阅读不如 Readwise，研究不如 Perplexity/Elicit。中间层产品最怕"样样 70 分"。
2. **没有出口**：不能导出、不能公开分享、不能推送到飞书/Slack。用户的成果被困在系统里。
3. **没有习惯回路**：没有周报/日报/推送，用户没有"每天/每周回来看一眼"的理由。
4. **第一次体验差**：无落地页、默认空列表、无引导；新用户 30 秒内看不到价值。
5. **速度与成功率**：10–18 分钟、58.5% 成功，和"一键 2 分钟"的产品竞争时，必须有明确的"值得等"的理由。
6. **小团队/个人维护的广度风险**：Admin 治理 35 个 API、约 3000 行控制台；消费侧雷达约 2000 行、专题约 1500 行。治理投入约为消费侧的 2 倍，边际收益已经很低。

**市场空位（值得押的 3 个）**

- **A. 中文技术团队的"决策记录"**：不是"这篇文章讲了什么"，而是"我们为什么选它/不选它，证据是什么，什么时候需要复审"。Elicit 有 evidence table，Thoughtworks 有 blip，没人把 decision log 做成产品。
- **B. 可解释的噪声治理**：把"为什么这条是噪声"展开成"哪一维拉低 + 哪句证据 + 置信度"，并让用户反馈改写评分。这是唯一能对抗"AI 摘要同质化"的护城河。
- **C. 闭环复用**：上次调研的结论，在下次开题时被自动带出（已有雏形），并在专题页被引用。这个复利效应是单点工具没有的。

### 5.4 三条路线，选一条

| 路线 | 形态 | 优势 | 风险 | 结论 |
|---|---|---|---|---|
| A. 个人技术情报助手 | 雷达 + 判断 + 周报 + Reader | 留存强、依赖轻、单人可维护 | 付费意愿弱、天花板低 | **适合作为入口** |
| B. 团队技术决策工作台 | 专题 + 决策记录 + 证据 + 分享 | 付费强、护城河深、竞品少 | 需要协作/权限/SSO，销售成本高 | **适合作为变现主线** |
| C. 中文 Deep Research 客户端 | 一键研究 + 快 + 导出 | 市场教育完成、需求明确 | 正面撞 Perplexity/Elicit，模型成本与速度都不占优 | **不建议作为主线** |

推荐组合：**用 A 拉新与留存，用 B 变现，Reader 作为差异化钩子**。当前产品的实现重心（治理、证据、审核）恰好更贴近 B，但缺少 B 必需的协作与决策记录；这是"能力与定位错位"的根源。

### P1（4–8 周，补标配）

1. **周报/推送**：每周一封"该看的 5 条 + 需要你决策的 3 条 + 专题变化"，邮件或飞书。Elicit 的 Routines 已经证明"定时 + 变化摘要"是刚需。日报链路删掉是对的，但"周报"应该回来。
2. **自建专题/关注词**：用户输入关键词/仓库/作者，生成个人 watchlist，复用现有聚合与议题管线。
3. **统一"我的调研"**：会话、任务、草稿同列；移动端入口不再沉底。
4. **公开分享页**：只读、可撤销、带证据与审核状态；解决 `published` 无出口。
5. **导出/API/MCP**：Markdown/PDF/RIS/JSON；读 API 让用户把知识带走（Readwise、Elicit 都已有）。
6. **⌘K 真命令面板**：最近搜索、专题/研究直达、回车聚焦。
7. **可解释评分**：评分展开为"哪一维拉低 + 证据句 + 置信度 + 局限"，默认折叠。
8. **Reader 高亮回流**：站外划线/笔记同步回研究库，否则"站外阅读"= 零沉淀。

### P2（季度，做差异化）

1. **团队空间**：成员、角色、共享专题、SSO；Admin 治理作为团队版钩子。
2. **决策记录（ADR 式）**：每个专题下记录"采纳/观察/放弃 + 理由 + 证据 + 复审日期"，形成团队技术决策台账。
3. **趋势与对比视图**：专题速度、来源多样性、方案对比矩阵。
4. **BYO key / 自托管套餐**：对齐 Inoreader/Elicit 的重度用户偏好；个人 $12–19/月、团队 $29–39/seat 是合理区间。
5. **移动端 PWA + 只读周报**：不做全功能 App。

### 明确不建议做

- **通用聊天/通用搜索**：打不过 Perplexity/ChatGPT，且会稀释"证据"定位。
- **全格式阅读器**：Readwise 已做到极致，投入产出比极低。
- **继续扩 Admin 治理**：现有 35 个 API 已超出当前用户规模所需。
- **原生移动 App**：PWA + 推送足够。
- **.pptx 导出**：Slides 提纲的定位（"不是 pptx"）是诚实的，别改。

### 9.2 资料检查（发布门禁）

同一份 32k 报告连续 6 次审核均以 `unavailable` 结束，`batch_count=0`，从未进入判读：

**结论：发布链路本身可用，卡点是"长报告事实审核"的成本与时延。**本次把预算改为 `300s + 字数/30`（上限 1,500s），并保留清单并发、失败批次拆分重试；但在当前本机模型网关下仍未跑通一次长报告审核，需要在更快 provider 或更轻的清单策略下复验。

### 9.5 审核收敛结果与发布门禁（同日续测）

审核链路改造后，同一份 32k 报告在 3 分 15 秒–3 分 45 秒内完成（此前为 `unavailable` 或整轮超时），34 个判读批次、201 条声明全部判读。但连续 3 次运行仍无法满足发布门禁：

- 第 1 次：1/32 批次失败（`invalid_output`），6 条声明 `execution_failed`，`coverage_status=insufficient`。
- 第 2 次：0 批次失败，但清单某个分块自报 `coverage_status=insufficient` → 整体 insufficient。
- 第 3 次：清单提示词调整后仍有 1/34 批次失败，`unverified_count=165`。
- `POST /publish` 返回 `400 VALIDATION_FAILED`：`publicationGate.status=coverage_insufficient`；同时 `openCount=172`、`unsupportedCount=171`——即便覆盖补齐，仍需要逐条处置 172 条声明才能发布，当前 UI 没有批量处置入口。

**结论：审核的"跑完"问题已解决（从不可用降到 3–4 分钟），剩下的是两件事：单批模型输出的稳定性，以及"172 条待处置声明"在发布流程里没有批量化出口。**后者比前者更影响产品可用性：真实 AI 报告几乎不可能靠人工逐条点头发布。

## 10. 发布流程改造（同日）

### 10.1 新的发布语义

把"审核"和"发布"解耦：

| 审核结果 | 旧行为 | 新行为 |
|---|---|---|
| 高风险声明被来源反证 | 硬阻断 | 硬阻断（唯一） |
| 普通声明未核验 | `needs_action` 硬阻断 | 作者显式确认后带披露发布 |
| 机器覆盖不完整 | `coverage_insufficient` 硬阻断 | 带披露发布，披露写明覆盖不完整 |
| 研究资料覆盖不足 | `research_insufficient` 硬阻断 | 带披露发布，披露写明资料缺口 |
| 核验尚未完成/未跑 | `unavailable` 硬阻断 | 作者显式确认后带披露发布 |

发布接口新增 `POST body: {"acknowledgeDisclosure": true}`；不带确认时返回 400，并在 `details` 中给出 `requiresDisclosureAcknowledgement`、完整 `disclosure` 计数与前 20 条未核验声明。发布页确认弹窗展示同样的计数并要求勾选；已发布详情页渲染"发布时披露"区块。

关键代码：

- `apps/web/src/lib/research-review-decisions.ts`：`getReviewPublishDisposition()` 把 gate 分成 `hardBlocked` / `requiresAcknowledgement` / `disclosure` 三部分，并生成未核验声明列表。
- `apps/web/src/app/api/researches/[id]/publish/route.ts`：事务内重新计算 disposition，只对高风险冲突抛 `RESEARCH_PUBLISH_REVIEW_GATE`；缺少确认抛 `RESEARCH_PUBLISH_DISCLOSURE_REQUIRED`。
- `apps/web/src/app/api/researches/[id]/route.ts`：已发布内容投影 `reviewDisclosureSummary` 与前 20 条声明。
- `apps/web/src/app/researches/[id]/page.tsx`：详情页"发布时披露"区块，默认展示 5 条，其余折叠。
- `apps/web/src/app/researches/[id]/edit/page.tsx`：发布按钮不再被 `needs_action` / `coverage_insufficient` 禁用；弹窗展示披露并要求勾选确认。

### 10.3 批量处置与核验徽章（已完成）

- 批量处置：新增 `POST /api/researches/[id]/review/decisions/batch`，一次最多接受 500 条低/中风险、仍缺直接依据的事实声明；所有记录共用一条作者理由，并保留各自的机器判读。来源冲突、高风险、已处理或非事实声明会整批拒绝，不做静默跳过。审核面板在存在 >1 条可接受项时显示“批量接受为待验证（N 条）”。
- 真实验证：克隆草稿 `4b2c9a10-1111-4222-8333-444455556666`（同一 32k 报告、172 条待处理）一次接受 12 条，返回 `201 acceptedCount=12`，`openCount` 从 172 降到 160；重复提交同一条返回 `400 already_decided`。
- 已核验徽章：详情页新增 `verification` 徽章。`verified`（已核验）只在当前审核 `completed + clear` 且无披露时出现；带披露发布显示 `disclosed`（带披露发布）；无当前审核则不显示。已分别用真实 published 记录验证两种状态。
- 发布后重新核验（已完成）：`POST /api/researches/[id]/review` 与引擎 worker 都允许已发布报告重新排队；详情页 owner/admin 可见「重新核验」。真实复跑 d28515a0：15:49:10 触发，15:58:59 完成（约 3 分 50 秒），`coverage_status=complete`、失败批次 0，但仍有 166 条 open，所以徽章仍是「带披露发布」——只有 clear 才升「已核验」。
- 仍缺：发布后不能再逐条/批量处置（决策接口只允许草稿），所以“先带披露发布、之后再清理”走不通；重新核验本身可以跑，但无法把 166 条 open 声明处理掉。这条是下一步要定的产品规则。
- 研究链路已把默认从“多轮（deep）”改为“单轮（standard）”，多轮改为显式选择；但产物仍是长报告，“决策问题 → 关键声明 → 短文”的结构化默认尚未实现。
