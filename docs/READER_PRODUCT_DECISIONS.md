# Reader 产品决策与 Monica 对照

> 观察与决策日期：2026-09-22–23。本文记录原网页插件形态、产品边界和平台整合原则；实现事实仍以代码、契约和 `PROJECT_STATUS.md` 的日期化验收为准。

## 1. 第一性原理

技术阅读的核心任务不是“随时能叫出一个聊天机器人”，而是：

1. 用户始终知道 AI 正在解释哪一段原文、哪一张图或哪一个页面范围。
2. 回答区分原文证据、必要背景、AI 推断、适用条件和未知项。
3. 代码、数字、图表坐标和技术标识不能因为翻译或覆盖而失真。
4. 阅读成果必须能回到原文，并能沉淀为以后可复用的研究结论。
5. 插件不应默认读取所有网页；用户动作、站点授权和数据去向必须可见。

因此 Reader 的北极星不是通用助手的功能数量，而是“从原文证据到可复用技术判断”的可靠闭环。

## 2. Monica 原网页 UI 观察

本次通过真实 Chrome 中已安装的 Monica 扩展观察网页右侧入口和侧栏，而不是 `monica.im/home` 产品主页。代表页面包括 Gmail 和公开技术文章。

| 观察到的模式 | 为什么有效 | Reader 的选择 |
| --- | --- | --- |
| 网页最右侧常驻、低占用的浮动入口 | 不要求用户离开当前任务，也不持续遮挡正文 | 采用。Reader 在用户明确启用站点后显示 42px 入口，不默认注入所有网页 |
| 原生侧栏承载完整交互 | 页面正文仍是主要阅读面，工具状态不会挤入内容流 | 采用。复杂操作留在 Chrome Side Panel |
| 自动绑定当前页面上下文 | 减少复制粘动解释“我在看什么” | 采用，但显示当前 URL、范围和覆盖边界 |
| 选区附近的快捷动作 | 用户意图和原文锚点同时明确 | 采用翻译、解读、追问、标注、摘录，并保留键盘路径 |
| 摘要中的编号来源跳转 | 回到原文的成本低 | 强化为精确 quote、offset、content hash 和版本失效规则 |
| 轻量快捷动作加深度聊天 | 高频动作快，复杂问题仍能连续讨论 | 采用，但回答固定拆分证据、背景、推断、限制和警告 |
| 通用 AI 工具箱、模型入口和大量跨场景能力 | 覆盖面广，但容易把阅读侧栏变成第二个应用启动器 | 不采用。Reader 不做模型市场、写作工具箱或通用 Agent 菜单 |
| 把全文总结、全文翻译、文章地图和风险取舍再次聚合成“本页工具” | 名称看似统一，但会和网页右侧入口、翻译控制区、文章分析区重复 | 不采用。右侧入口只启动高频页面动作；侧栏只承载分析结果、历史和连续对话，避免同一动作多处出现 |

### 2.1 真实交互清单

此前在独立浏览器窗口中按阅读路径逐项操作 Monica，记录的不是主页宣传能力，而是用户在文章页面上实际能看到和点击的状态：

| 路径 | Monica 的反馈 | 对 Reader 的启发 |
| --- | --- | --- |
| 页面右侧入口 | 入口始终在视口边缘，按钮很小；悬停或点击后才暴露动作名称 | Reader 的入口需要同时满足“可发现”和“不遮挡”。字母或希腊字母不如带语义的图标加 tooltip，页面动作不应只靠猜 |
| `Summary this page` | 直接使用当前页面，不需要先复制正文；结果可以继续追问 | 全文总结必须是一等入口，并在结果中保留“当前页面/当前版本”的上下文 |
| `Enable translation` | 翻译是独立的页面动作，不和总结结果混在同一块 | 翻译是阅读变换，不是聊天消息；应保持单独的进度、暂停、恢复原文和失败重试 |
| `Read this page` | 适合快速消费页面，属于阅读入口而不是分析报告 | Reader 暂不复制通用朗读能力；技术文章优先把“听懂”替换成结构化摘要、证据和边界 |
| `Chat with link` / Quick Ask | 简短问题有时在轻量窗口直接得到答案，复杂追问才进入完整聊天 | Reader 可以引入“快速回答”层，但必须明确回答范围；不能让短答案失去证据和继续讨论入口 |
| 连续追问 | 当前页面上下文、推荐追问和上一轮回答保持连续 | Reader 的聊天不能只是一次性的结果卡片；历史详情和“继续讨论”必须回到原有侧栏上下文 |
| 结果操作 | 复制、分享、切换模型、生成思维导图等操作紧跟回答出现 | Reader 只保留技术阅读真正需要的复制、引用回跳、收藏、标注、重试和继续追问，避免把工具菜单做成第二个产品 |
| 选中文字 | 选区动作和页面动作分层，用户能感知是在问“这段”而不是问“整页” | Reader 需要把作用范围放在按钮附近，而不是只依赖“追问选段/问整页”这类相似文案 |
| 历史和 Memo | 结果可以沉淀为后续可找的内容，而不是只存在当前浮层 | Reader 的历史应展示问题、回答、页面、选段和版本；保存结论与聊天记录要区分 |

### 2.1.1 官方阅读文档核对

除网页实测外，本次核对了 Monica 官方帮助文档中的阅读相关入口：

- [阅读助手](https://monica.im/help/zh-cn/Features/Read)：把网页阅读动作组织在当前页面上，重点是页面摘要、翻译和选区操作。
- [网页总结](https://monica.im/help/zh-cn/Features/Summarize/Summarize-Webpage)：总结直接绑定当前网页，不要求用户先复制全文。
- [网页翻译](https://monica.im/help/zh-cn/Features/Translate/Webpage_translation)：翻译是独立的页面变换，不是聊天消息中的一段译文。
- [Memo](https://monica.im/help/zh-cn/Features/Memo)：把阅读过程中产生的内容沉淀为可再次查找的记录。
- [简化文章](https://monica.im/help/zh-cn/Features/Simplify-Article)：降低文章阅读门槛，但仍然属于当前页面的阅读动作。
- [Toolkit](https://monica.im/help/zh-cn/Features/Toolkit) 与 [PowerUP](https://monica.im/help/zh-cn/Features/PowerUP/Introduction)：属于通用工具扩展面，不应直接成为技术 Reader 的首屏信息架构。

文档与实测共同支持一个结论：Monica 的可借鉴点主要是动作与上下文的贴合，而不是把所有能力搬进侧栏。Reader 应把“总结本页、翻译本页、问当前范围”做得更直接，同时把证据回跳、版本失效和技术适用边界做得更严格。

### 2.1.2 2026-09-23 独立窗口复测记录

本次在单独的 Chrome 窗口打开 `https://claude.com/blog/the-ai-native-sdlc-playbook`，实际点击了页面右侧入口和侧栏动作。以下只记录屏幕上已经出现的结果：

| 已点击动作 | 实际结果 | 对 Reader 的判断 |
| --- | --- | --- |
| 页面右侧阅读入口 | 打开原生侧栏；顶部显示 `Summarize this page`、当前页面标题和 URL，底部始终保留聊天输入框 | “当前页面 + 当前范围 + 输入框”是 Monica 体验最值得借鉴的骨架。Reader 需要让用户一打开侧栏就能继续问，而不是先寻找聊天入口 |
| 页面总结 | 返回 `Summary`、`Key Points`、推荐问题和结果操作；总结会列出类似 `6 7` 的原文位置标记，并提示 `Jumping to original text is in beta stage` | 推荐问题和结果动作值得借鉴；位置标记如果不能稳定回跳就不应伪装成引用。Reader 应只显示已通过 quote/hash 校验的数字证据 |
| 选中原文后的 Quick Actions | 工具条出现在选段下方；实际看到的动作包括 `Summarize`、`Translate`、`Explain this`、`Grammar`、`Rewrite`、`Expand`、`Answer this question`、`Explain Codes`、`Memo`、`Highlight`。代码选段会更适合 `Explain Codes`，普通选段则以通用动作居多 | 交互位置和“选段即上下文”值得借鉴，但技术 Reader 不应照搬通用写作动作。首层只保留“总结这段、解释这段、翻译这段、问这段”，保存类动作放到第二层，并始终显示选段范围 |
| Quick Ask 风险问题 | 对 “What is the single biggest risk...” 的回答给出“治理和评审容量跟不上 AI 产出速度”，引用了原文句子，并进一步落到 hooks、branch protection、managed settings 和人工 release gate | 技术回答质量可以达到“可用的第一轮判断”。但回答必须保留来源、适用边界和继续追问入口，不能只复制 Monica 的无证据摘要 |
| 结果动作栏 | 回答下方出现 Share、重新生成、复制、选择其他模型、Suggested follow-ups；追问仍留在同一侧栏 | Reader 应把复制引用、保存、继续追问和回原文放在回答附近；模型切换可以保留在设置或回答菜单，不应成为首屏主导航 |
| 侧栏 `Translate` | 打开的是独立的文本翻译工具，有源语言、目标语言和输入框，不会把当前页面直接翻译 | 页面翻译和文本翻译是两个不同动作。Reader 的页面入口必须避免把两者共用一个模糊标签 |
| 页面浮动翻译入口 | 显示 `Enabling web translation...`，随后原网页标题、正文和元数据在当前页面内变成中文，侧栏仍保留 | 这是“页面变换”而不是聊天消息。Reader 当前的全文翻译、进度、恢复原文和失败项设计方向正确 |
| 页面 Audio 入口 | 新开 `monica.im/en/ai-podcast` 标签，URL 输入框已经填入当前文章；页面有 Recent 播客列表和语言/主持人配置 | 仅作为 Monica 的能力观察，不纳入 Reader 产品范围或验收项 |
| `Generate mind map` | 侧栏出现 `Call Skill: Mind Map`，短暂显示一个空白产物区域和“已生成”文案；本次屏幕上没有可读的思维导图内容 | 仅作为 Monica 的能力观察，不纳入 Reader 产品范围或验收项；Reader 只保留可读的章节树、证据节点和稳定回跳 |

这次复测还暴露了 Monica 的两个产品级取舍：

1. **侧栏不只是结果面板，而是持续会话容器**：页面总结、Quick Ask、推荐追问、模型切换和结果操作在同一滚动上下文中；这正是 Reader 目前最需要补齐的体验。
2. **动作入口与产物类型不完全一致**：同一个侧栏同时承载页面总结、文本翻译、页面变换、技能调用和跨页 Podcast。通用助手可以接受这种广度；技术 Reader 必须按“页面变换 / 当前范围问答 / 可保存研究产物”重新分层，否则会重现功能多但职责不清的问题。

本次未完成的真实点击项：选区菜单中的每个动作、Memo 写入/回看、模型切换后的重新回答、分享动作和完整历史回到原会话。原因是测试期间普通 Chrome 的前台窗口被用户侧状态变化重新夺焦，CUA 拒绝继续使用旧窗口绑定；这些项目不能仅依据文档或已有截图宣称已验收。

### 2.1.3 官方文档带来的补充判断

官方帮助文档把 Monica 的阅读能力拆成了几个很清楚的动作层：

- 阅读助手提供当前页面的摘要、选区快捷动作和侧栏继续提问；选区动作可以按用户习惯配置，而不是所有动作都必须挤在首屏。
- 网页总结强调当前页面的一键总结、继续追问和回到原文；总结中的定位能力只有在确实能把用户带回对应文本时才有价值。
- 网页翻译是当前页面的变换，译文与原文保持明确关系；文本翻译则是另一种输入工具，不能共用一个模糊的“翻译”入口。
- Memo 的价值不只是保存一条结果，还包括从保存内容继续对话；这说明“历史记录”和“知识结论”应当分成两个可理解的对象。
- Toolkit / PowerUP 的可扩展能力适合通用助手，但不应成为技术 Reader 的默认首屏。技术 Reader 应优先让用户理解当前范围、证据和限制。

因此本轮实现采用了一个更窄的状态机：初始页面只显示文章动作和选段动作；点击“问整页/问这段”、总结或解读后才展开聊天容器，聊天一旦展开便保持同一会话和固定输入区。这样借鉴了 Monica 的连续会话，但不把空聊天面板强行放在文章分析前面。

### 2.1.5 2026-09-23 Monica 前台 Chrome 复测

本次在已安装 Monica 的普通 Chrome 窗口重新打开同一篇公开文章
`https://claude.com/blog/the-ai-native-sdlc-playbook`，并实际点击右侧入口、发送问题和观察结果状态。普通 Chrome 窗口后来被用户操作夺焦，因此没有把尚未重新点击的动作记成已验收；以下只记录本轮确实看见的状态。

| 实测路径 | 屏幕上的结果 | 结论 |
| --- | --- | --- |
| 右侧书本入口 | 页面右侧展开约一半宽度的工作区；顶部保留页面标题和 URL，底部固定输入框；页面内容仍在左侧可见 | 这是比“跳转到独立聊天页”更好的阅读骨架。当前页面、当前范围和输入框应在同一容器内 |
| `Summarize this page` | 先显示 `Page summary` 和加载占位符；等待后没有产生摘要 | 入口反馈有，但失败状态不够明确，不能只停在省略号 |
| Quick Ask | 发送 “What is the single biggest risk this article identifies, and which mechanism is meant to control it?” 后，Monica 最终明确回复没有拿到文章内容、上一轮总结只有占位符，并要求用户粘贴正文 | Quick Ask 的输入和结果容器很顺，但页面上下文绑定并不可靠。Reader 必须在发送前显示正文抽取状态，失败时提供重试、查看抽取内容和改用选段 |
| 结果操作区 | 回答下方出现 `Share`、重新生成、复制、更多操作、选择其他模型；随后出现 `Suggested follow-ups`，追问仍留在同一侧栏 | 结果动作紧邻答案，连续对话成本低。Reader 应保留复制、继续追问、保存和回原文，分享与模型切换放入次级菜单 |
| 模型选择 | 结果区出现 `Choose another model to answer`，可切换多个模型 | 这是通用产品的高频能力，但 Reader 不应把模型切换做成主阅读动作；应在设置或答案更多菜单中提供，并显示当前模型 |
| 页面动作胶囊 | 侧栏下方同时显示 `Translate`、`Calendar`、`Document`、`Mindmap`、`Mermaid`、`All` | 这套胶囊的可发现性很好，但职责混杂。技术 Reader 只需要“总结、翻译、文章结构、风险取舍”四类可验证产物，不能因为入口好看就复制全部技能 |
| 右侧全局导航 | 显示 `Chat`、`Image`、`Video`、`Audio`、`Discover`、`Memo`、`More` | Monica 把阅读、创作和工具市场放在一个壳里，适合通用助手；Reader 应将页面阅读入口、当前范围聊天和研究沉淀分层，避免出现第二个启动器 |

本轮新增的产品判断：

1. **加载态必须是可解释状态机**：`读取正文`、`正文可用`、`正文为空/被保护`、`模型生成中`、`生成失败`必须区分；无限省略号会让用户误以为模型仍在工作。
2. **页面上下文必须可见且可核验**：在发送问题前显示正文字符数、识别到的标题/章节数量和当前范围；内容为空时禁用“问整页”，但仍允许用户选择一段后问。
3. **快速回答不是证据豁免**：Monica 的 Quick Ask 可以把短问题放进轻量结果区，这是值得借鉴的交互层；但技术 Reader 的轻量回答仍必须带页面范围、证据入口和“继续在侧栏讨论”。
4. **技能胶囊不等于产品边界**：`Calendar`、`Document`、`Mindmap`、`Mermaid` 是通用工具的可发现入口，不应被误判为技术文章阅读的必需功能。文章地图和 Mermaid 只有在产物真实可读、可回到证据时才进入验收。

### 2.2 目前 Reader 的体验差距

代码和隔离浏览器回归已经证明 Reader 的页面识别、证据锚点、结构化回答、会话恢复和数据边界可工作；本轮已收口首屏空聊天和历史动作文案，但从首次使用的认知负担看，仍有三个明显落差：

1. **第一步不够直接**：页面入口可以触发总结和翻译，但入口上的 `Σ`、`译` 和 `R` 对新用户不是自解释的；Monica 的 tooltip、按钮命名和动作反馈形成了完整闭环。
2. **结果层级仍然偏重**：Reader 的文章分析卡片和结构化回答信息密度高，短问题仍然会进入完整聊天区域。用户只想确认一个事实时，需要先理解工作台结构。
3. **选区工具条仍需更接近原文**：侧栏中的选区卡片已明确区分“针对这段”和“聊天范围”，但网页选区工具条还可以进一步借鉴 Monica 的“选完立即行动”，减少从网页回到侧栏的距离。

### 2.3 采纳顺序

| 优先级 | 改动 | 验收信号 |

### 2.4 明确不照搬的能力

- 不做 PowerUP 市场、通用插件市场或模型市场。它们扩大的是工具覆盖面，不直接提高技术文章的证据质量。
- 不做 AI Podcast、Mindmap、通用朗读、视频生成或图像生成。它们不属于当前技术文章证据阅读闭环，也不进入 Reader 的实现和验收范围。
- 不做“架构代码生成”作为默认快捷动作。代码生成需要仓库、运行环境、依赖版本和测试闭环，单篇网页通常无法提供足够上下文。
- 不用一个模糊的“本页工具”容器重新包装所有动作。页面入口、翻译控制、分析结果和聊天必须有清晰的职责边界。

## 3. Reader 的差异化

- **技术文章身份**：优先识别文章、小节、代码块、表格、图示、GitHub README 和 Zread 页面，不把所有网页当作同一种聊天上下文。
- **证据优先**：模型证据必须能在当前页面精确定位；内容版本变化后旧证据标记失效，而不是跳到相似句子。
- **适用边界**：回答不仅给结论，还要说明假设、限制、未知项和可能的反例。
- **代码与图示保护**：代码默认不翻译；图片只有在坐标、置信度和排版都安全时才覆盖，否则保留原图并旁译。
- **知识沉淀**：收藏不是聊天消息归档，而是用户确认过的摘录、笔记、AI 结论、标签和来源。
- **雷达闭环**：雷达负责发现、元数据和排序；Reader 在原网页负责理解；确认成果再回到研究库。

## 4. 双模式产品边界

### 独立模式

- 不要求 Deep Research 账号或 Web 服务。
- 用户配置自己的 OpenAI-compatible 或 Anthropic-compatible 模型。
- 会话、标注、收藏、任务和有界翻译缓存保存在浏览器 IndexedDB。
- 支持 JSON 导入导出和完全独立安装。

### 平台模式

- 通过 PKCE 连接 Deep Research，不把账号密码交给扩展。
- 文本技术问答使用平台 AI engine。
- PostgreSQL 中的 `ReadingSession` 是跨设备会话权威；研究库 `Research` / `ResearchSource` 是确认成果权威。
- 本地 IndexedDB 仍保留恢复缓存和同步失败保护，不能成为唯一副本。
- 网页全文档案、图片字节、翻译缓存和 API Key 不写入平台数据库。
- 图片理解可继续使用独立模式配置的视觉模型，避免平台被迫接收图片字节。

## 5. 雷达到原文

`external_reading` 雷达详情先显示安装和数据边界，再用带来源标记的 URL 打开原文：

```text
deep-research-source=radar
deep-research-summary=<summary UUID>
```

已安装并启用 Reader 时，content script 识别来源标记、移除标记后生成 canonical URL，并在侧栏提示“来自 Deep Research 雷达”。没有安装扩展时，外部站点本身无法被平台注入安装提示，因此安装引导必须在离开雷达之前完成，不能假装平台能控制任意第三方网页。

## 6. 明确不做

- 不默认申请所有网站读取权限。
- 不在雷达数据库复制所有外部文章全文。
- 不把未确认的聊天输出自动创建为正式研究。
- 不因平台不可用而破坏独立阅读。
- 不用相似文本替代失效的精确证据锚点。
- 不把安全降级描述成图片翻译成功。

## 7. 验收要求

- 真实 Chrome 中检查右侧入口、原生侧栏、选区动作和窄宽度布局。
- 确定性模型验证暂停、取消、重试、恢复、Worker 重启和 SSE 流。
- 真实模型验证供应商协议、技术正文、图片和恢复路径。
- 隔离 PostgreSQL 验证 migration、会话幂等、保存幂等、用户隔离和令牌撤销。
- 正式构建必须保持 `host_permissions=[]`，HTTP(S) 只通过 optional permission 按需申请。
- 独立 ZIP 和平台模式必须来自同一套核心阅读实现，避免形成两个行为漂移的产品。
