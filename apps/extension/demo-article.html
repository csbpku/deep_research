Bounded queues for background work

Reader demo article · about 700 words · safe to translate and ask about

A background pipeline in the browser has to keep the page responsive while it reads, translates, or analyses content. The most useful primitive for that job is a bounded queue: producers enqueue work, workers take it off the queue, and the queue itself refuses to grow without limit.

Why a bound is not a performance limit

Bounded queues keep browser work responsive because cancellation can stop stale requests before they consume more model capacity. The bound is not there to slow the system down; it is there to make the cost of new work visible to the producer.

When the queue is full, the producer has three options: wait, drop the oldest item, or fail the request. Each choice has a different failure mode, and the right one depends on whether the work is interactive or background.

The trade-off. A small bound makes backpressure appear early and keeps latency predictable, but throughput suffers when requests arrive in bursts. A large bound absorbs bursts but hides overload until memory and latency both degrade.

What cancellation changes

If a user closes the sidebar or changes the selected passage, the queued work is no longer useful. Cancellation has to be part of the queue contract rather than an afterthought: an aborted job must not hold a worker slot, and its result must never be applied to the page after the page has changed.

Reliable reading tools make uncertainty visible and keep the original document in control.

Implementation sketch

async function drain(queue, worker, signal) {
  const active = new Set();
  while (queue.length || active.size) {
    if (signal.aborted) break;
    while (active.size < 4 && queue.length) {
      const task = queue.shift();
      active.add(worker(task).finally(() => active.delete(task)));
    }
    if (active.size) await Promise.race(active);
  }
}

Choosing capacity

Measure the p95 latency of one request and the burst size you expect. Capacity should be large enough to absorb one burst and small enough that a full queue still drains in a few seconds. In practice, four parallel workers and a queue of twenty-four items cover most reading workloads.
